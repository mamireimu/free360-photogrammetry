# free360-photogrammetry

360度カメラで歩き撮りした動画から、無料のOSSだけでテクスチャ付き3Dモデルを作る研究用パイプラインです（FFmpeg + COLMAP + OpenMVS、Docker / CUDA）。

屋内を歩き撮りした動画から、VRChatのワールドの下敷きにできる3Dモデルを作る実験をしています。
有料ソフトを使わずに、無料のOSSだけでどこまでできるかを記録しています。
出力はそのままワールドにする完成品ではなく、Blenderで組み直すための下敷きを想定しています。

> **状態：研究中です。** 部屋の配置は復元できていますが、白い壁の穴、光沢のある床の陥没、面の粗さが残っています。
> 実データでの結果は[研究メモ](#研究メモ)にまとめています。

## 必要なもの

- Linuxホスト（Debianで確認）、Docker、NVIDIAドライバー、NVIDIA Container Toolkit
- NVIDIA GPU（Tesla T4×4で確認。ビルドは既定で `sm_75`（T4）と `sm_89`（RTX 40シリーズ）向け）
- 十分なRAMとディスク。12分・3fps・1,024pxの動画（約13,000枚）で、メモリ約75GB、ディスク約405GBを使いました（[参考指標](#参考指標処理時間メモリディスク)）
- 入力：スティッチ済みの正距円筒図法（equirectangular）、横縦比2:1の360度MP4

## 使い方

### ビルド

~~~bash
git clone https://github.com/mamireimu/free360-photogrammetry.git
cd free360-photogrammetry
docker build --progress=plain -t free360-photogrammetry:1 .
~~~

COLMAP・Ceres・OpenMVSをソースからビルドするため、初回は時間がかかります。`BUILD_JOBS`（既定4）で並列数を変えられます。並列数を上げるとメモリも多く使います。
別の世代のGPUを使う場合は、`CUDA_ARCHITECTURES` で対象を指定します（例：RTX 30シリーズなら `86`）。

~~~bash
docker build --build-arg BUILD_JOBS=16 --build-arg CUDA_ARCHITECTURES=89 -t free360-photogrammetry:1 .
~~~

旧名 `mp4-to-model:1` でビルドしたことがあれば、同じDockerビルダーのキャッシュが使われます。

### 実行

入力・出力のパスを実際のものに置き換えてください。

~~~bash
bash run.sh /data/room360.mp4 /data/result --fps 3
~~~

- GPUを省略すると、見えている全NVIDIA GPUを使います（`--gpus 0,1,2,3` のようにも指定できます）。
- 短い区間で試すときは `--start 120 --duration 60` のように区間を指定します。
- 途中でカットされた動画は、カットのない区間ごとに処理してください（[品質の限界と仕上げ](#品質の限界と仕上げ)）。
- パスにカンマは使えません。空白を含むパスは引用符で囲んでください。

止まったときや設定を変えたいときは、同じコマンドに `--resume` を付けて再実行します（[途中から再開する](#途中から再開する)）。

## 処理の流れ

| 工程 | 内容 | 使うもの |
|---|---|---|
| 01_frames | 動画を1回だけデコードし、時刻ごとに6方向（前・右・後・左・上・下）の画像へ投影 | FFmpeg v360（NVDEC対応） |
| 02_features・02_rig | 特徴点抽出。同じ時刻の6方向を、相対回転が既知のリグとして登録 | COLMAP（CUDA） |
| 03_matches・03_loops | 時間順の近傍との照合と、離れた時刻の似た画像との照合 | COLMAP sequential / vocab_tree matcher |
| 04_sparse | カメラ位置の推定。既定は全時点を一括で解く方式 | COLMAP global_mapper（CUDA版Ceres） |
| 05_undistort | 高密度化用に画像を整える | COLMAP |
| 06_depth | 画像ごとの深度推定。最も時間がかかる工程 | COLMAP patch_match_stereo（CUDA） |
| 07_masks・07_fusion | 深度を点群に統合。撮影者が写る真下向き（cam5）は除外 | COLMAP stereo_fusion |
| 08_import | OpenMVS形式へ変換 | OpenMVS InterfaceCOLMAP |
| 09_mesh | メッシュ化 | OpenMVS ReconstructMesh |
| 09b_floor | 床より下に沈んだ頂点を床へ戻す | このリポジトリの処理 |
| 10_texture | テクスチャを貼ってOBJを書き出す | OpenMVS TextureMesh |

## 出力

出力先には次のファイルができます。

| ファイル | 内容 |
|---|---|
| model.obj、model.mtl、テクスチャ画像 | 完成モデル。3つを同じ場所に置いて使う |
| report.json | 登録画像数、面数、選択したGPU、デコード方式など |
| selected_model.json | 採用した復元成分と登録率 |
| decode.json | NVDEC／CPUのどちらでデコードしたかと、その理由 |
| mesh_floor.ply、floor.json | 床の処理後のメッシュと、その記録（上方向、目の高さ、動かした頂点数） |
| dense/fused.ply | 高密度点群。メッシュ化の前の形を確認できる |
| logs/ | 工程ごとのログ。実行中は `tail -f` で進み具合を確認できる |
| state.json | 再開用の記録 |

モデルの実寸と向きは決まっていません。Blenderなどで縮尺と向きを合わせてください。

## 調整項目

| オプション | 既定値 | 用途 |
|---|---:|---|
| --start | 0 | 開始位置（秒） |
| --duration | 動画末尾まで | 処理する秒数 |
| --fps | 1 | 1秒あたりの時間サンプル数。屋内の歩き撮りでは3が目安 |
| --face-size | 自動 | 各方向画像の一辺（px）。既定では元動画の解像度に合わせる（横幅3840なら1072、5760なら1600）。これより大きくしても引き伸ばしになるだけで、深度推定の時間とディスクが増える |
| --faces | 6 | 4なら水平のみ、6なら上下を含む |
| --gpus | all | 全GPU、または `0,1,2,3` のような指定 |
| --decode | auto | auto／cuda／cpu。autoはNVDECを試し、失敗したら理由を表示してCPUで再試行 |
| --threads | CPU数 | CPU工程のスレッド数。再開時の設定比較には含まれない |
| --overlap | 8 | 時間順に照合する近傍の幅 |
| --max-frames | 2000 | 時間サンプル数の上限。超えると開始前に停止する |
| --loop-images | 20 | 離れた時刻から似た画像を探して照合する数（1枚あたり）。0で無効 |
| --sfm | global | カメラ位置推定の方式。incrementalは従来のCOLMAP mapper |
| --min-registered-ratio | 0.3 | 最大の復元成分に登録された画像の最低割合。下回ると高密度化へ進まない |
| --target-faces | 500000 | 目標面数。範囲全体に配るので、広い場所では増やす（例 3000000） |
| --texture-size | 8192 | テクスチャ1枚の最大サイズ。Unityでは取り込み設定の Max Size も合わせる |
| --virtual-face-images | 3 | 同じ平面で、この枚数以上の写真に共通して写る三角形をまとめて1枚の写真から貼る。色のまだらが減る（0で無効） |
| --free-space-support／--no-free-space-support | 有効 | メッシュ化で、点の少ない面（白い壁など）を視線の情報から残す |
| --close-holes | 300 | この辺数までの穴を面でふさぐ（OpenMVSの既定は30、0で無効） |
| --smooth | 8 | メッシュの平滑化の回数。深度の誤差による凹凸をならす。大きいほど角も丸くなる（OpenMVSの既定は2、0で無効） |
| --floor／--no-floor | 有効 | 床より下に沈んだ頂点を床の高さへ戻す |

目安：1分×1fps×6方向で約360枚です。時間サンプル数は「秒数×fps」で、`--max-frames` を超える場合は `--max-frames`・`--fps`・`--duration` を調整してください。

## 途中から再開する

同じ入力・同じ設定・同じ出力先で `--resume` を付けると、完了した工程を飛ばして続きから実行します。

~~~bash
bash run.sh /data/room360.mp4 /data/result --fps 3 --face-size 1024 --resume
~~~

- `--face-size` の既定が自動になる前に作ったジョブは、当時の値（例：`--face-size 1024`）を付けて再開してください。付けないと設定の違いとして停止します。
- 元動画はSHA-256で照合します。動画や設定が違うと、違う項目を表示して停止します。
- 次の設定だけは、変えて再開すると影響する工程から作り直します。深度推定（06）などの前の工程はそのまま使います。

  | 設定 | 作り直す工程 |
  |---|---|
  | --target-faces、--free-space-support、--close-holes、--smooth | 09（メッシュ）から |
  | --floor／--no-floor | 09b（床の処理）から |
  | --texture-size、--virtual-face-images | 10（テクスチャ）から |

- 処理内容が変わった版に更新したときは、変わった工程から自動で作り直します（詳細は[CHANGELOG-ja.md](CHANGELOG-ja.md)）。
- 出力を手で編集・移動・削除してからの再開は対象外です。
- 同じ出力先への二重起動はファイルロックで防ぎます。

## 結果を確認する

ホストのPython 3（追加パッケージ不要）で動く確認用スクリプトがあります。

~~~bash
python3 diagnose_frames.py /data/result
python3 export_trajectory.py /data/result
~~~

- `diagnose_frames.py`：抽出した枚数、復元がいくつに分かれたか、どの時刻の照合が弱いかを表示します。
- `export_trajectory.py`：カメラの経路（時刻順に青→緑→赤）と疎な点群をPLYに書き出し、経路が飛んだ所を時刻つきで一覧にします。CloudCompareやMeshLabで開いて確認します。2つのスクリプトは同じフォルダに置いてください。
- `dense/fused.ply`：穴が点群の段階で既に開いているのか、メッシュ化で開いたのかを見分けられます。

GPUの使用状況は `nvidia-smi dmon -s u` で確認できます（動画デコードはdec列）。

## 品質の限界と仕上げ

### 素材の条件

- カメラを持って移動しながら撮った素材が必要です。
- 白い壁、鏡、ガラス、光沢のある床、動く人、ブレ、ステッチのずれは復元できないか、崩れの原因になります。
- 同じ場所に戻ってくる動画はつながります。途中でカットして場所が飛ぶ動画は、1つの復元にまとまっても位置がずれることがあります。カットのない区間だけを使ってください。
- 照合で使う語彙ツリーは、初回にCOLMAPがダウンロードします（インターネット接続が必要）。

### 自動ではやらないこと

- 復元が分かれた場合は、登録画像数が最多の成分だけを使います。
- 実寸と向きは決めません。
- 撮影者の除外は真下向き（cam5）だけです。ほかの向きに写る撮影者や通行人のマスク、ブレた画像の選別、部屋ごとの分割はしていません。
- テクスチャ（10）はcam5の画像も使うため、床に撮影者の色が残ることがあります。
- コライダー、スポーン地点、ライト、Quest向けの最適化は別途必要です。

### 床の陥没を戻す処理（09b_floor）

光沢のある床は照明や天井を映すため、映った像の距離が床の深さとして復元され、床がすり鉢状にへこみます。
模様の少ない床や、浅い角度でしか見えない床も、深度が不安定でへこみや穴になります。
そこでメッシュを作ったあと、テクスチャを貼る前に次の処理をします。

- 上方向：正面向き画像（cam0）の下方向の逆。360度カメラの水平補正が効いている前提です。
- 床の高さ：歩いた経路を区画に分け、区画ごとのカメラの高さから「目の高さ」を引いた高さ。目の高さは、カメラ直下の頂点で最も多い高さの差から決めます。
- 床より下（目の高さの2倍まで）と、床のすぐ上（目の高さの3%以内）の頂点を床の高さに合わせます。歩いた経路から目の高さの5倍以上離れた所と、それより深い所は動かしません。

注意点：

- 穴（面がない所）は埋まりません。
- 階段や坂は、カメラの高さの変化に沿った斜面になります。段は残りません。
- 床に置かれたごく低い物は床に潰れます。気になる場合は `--no-floor` で無効にします。

### VRChatで歩き回れるワールドにする流れ

スキャンをそのままワールドにするのは難しいので、下敷きにして作り直します。

1. このパイプラインで部屋の配置と、壁や床の見た目を取る
2. Blenderで床を水平にし、ドアの高さなど実寸のわかる所で縮尺を合わせる
3. スキャンを下敷きにして、床・壁・天井を板や箱で組み直す
4. スキャンの色を、組み直したモデルのテクスチャにベイクする
5. Unityでコライダー、ライトのベイク、VRChat SDKの設定をする

この流れなら、スキャンの穴や膜はほとんど問題になりません。大事なのは、部屋の配置が正しいこと（経路が飛んでいないこと）と、壁や床の模様がにじまずに撮れていることです。
スキャンをそのまま置く場合も、歩く面にはスキャンのメッシュではなく、床の高さに置いた板や箱のコライダーを使うほうが確実です。

## 研究メモ

無料のツールだけで、歩き撮りの360度動画からVRChatで歩き回れるワールドをどこまで作れるかを調べています。
このパイプラインはすべてOSSで組んでいて、工程ごとに差し替えて比べられます。

### 実データでの結果（屋内、Insta360系の360度動画）

| 素材と設定 | 結果 |
|---|---|
| 17分・カットあり、1fps、1,024px | 全6,186枚が1つの復元に登録されたが、12:00のカットをまたぐ照合は1組だけだった |
| 同じ動画、ループ照合あり | カットをまたぐ照合は増えたが、経路は12:00付近で300単位以上飛び、カット後が別の場所に組み立てられた。モデルは崩れて使えなかった |
| カットを除いた12分、3fps、1,024px | 全12,966枚が1つの復元に登録され、経路の飛びもなし。深度推定（06）は約17時間。点群統合（07）はRAM 31GBでは足りず停止した（exit -9）ため、キャッシュを減らしRAMを64GBにした |
| 同上の完成モデル | 部屋の形は出たが、穴・膜状のふくらみ・浮いた破片が多い |
| 同上、撮影者マスク入り | 面が大きく粗い（50万面を範囲全体に配分）。光沢のある床が陥没し、白い壁に穴が開く |
| 同上、300万面＋床の処理 | テクスチャ（10）がRAM 64GBで停止（exit -9）。再評価中 |

### 参考指標（処理時間・メモリ・ディスク）

計画を立てるときの目安です。実測値と、そこからの計算値を分けて書いています。

**実測した環境**：Tesla T4×4、CPU 16→32コア、RAM 31GB→64GB（途中で増設）、Docker on Debian

| 項目 | 素材と設定 | 値 | 種別 |
|---|---|---|---|
| 画像数 | 17分・1fps・6方向 | 6,186枚 | 実測 |
| 画像数 | 12分・3fps・6方向 | 12,966枚 | 実測 |
| カメラ位置の推定（04） | 約6,000枚、cuDSS対応Ceres（GPU） | 約13分 | 実測 |
| 深度推定（06） | 12,966枚、1,024px、T4×4 | 約17時間 | 実測 |
| 点群統合（07） | 12,966枚、キャッシュ8GB | RAM 31GBで停止（exit -9） | 実測 |
| 点群統合（07） | 12,966枚、キャッシュ4GB | RAM 64GBで完了 | 実測 |
| テクスチャ（10） | 12,966枚、300万面 | RAM 64GBで停止（exit -9） | 実測 |
| メモリ（最大） | 12分・3fps・1,024px | 約75GB | 実測 |
| ディスク（出力先全体） | 12分・3fps・1,024px | 約405GB | 実測 |
| 深度・法線マップ | 1,024px | 1枚あたり約32MB | 実測から計算 |
| 深度・法線マップ | 1,536px | 1枚あたり約72MB | 計算（面積比2.25倍） |

**見積もりの式**

- 画像数 ＝ 秒数 × fps × 6方向（`--faces 4` なら4方向）
- ディスク ≒ 画像数 × 32MB（1,024px）、× 35MB（1,072px）、× 72MB（1,536px）。画像そのものやメッシュは数GB〜十数GBなので、深度・法線マップがほぼすべて
- 深度推定の時間は、おおむね画像数 × 画像の面積に比例します（T4×4・1,024pxで約13,000枚あたり17時間）

**ディスクを減らす**

- 深度推定の途中結果（`*.photometric.bin`）は点群統合では使わないので、06が終わったら消せます（約半分）。

  ~~~bash
  find /data/result/dense/stereo -name '*.photometric.bin' -delete
  ~~~

- `*.geometric.bin` を消すと `--resume` が06から先に進めなくなり、07のやり直しもできなくなります。07をもうやり直さないと決めてから、`dense/stereo` を丸ごと消してください。

### 無料で使える選択肢

| 工程 | 今使っているもの | 比較対象 | メモ |
|---|---|---|---|
| カメラ位置の推定 | COLMAP global_mapper | COLMAP incremental mapper（`--sfm incremental`）、Meshroom（AliceVision） | |
| 高密度化 | COLMAP patch_match_stereo | OpenMVS DensifyPointCloud | OpenMVSはイメージに入っている。GPUで動かすにはCUDAを有効にしてビルドし直す |
| メッシュ化 | OpenMVS ReconstructMesh | Poisson（CloudCompare・MeshLab） | Poissonは穴をなめらかにふさぐので、屋内の壁に向く |
| テクスチャ | OpenMVS TextureMesh | Blenderのベイク | 作り直したモデルに焼き付けるならBlender |
| 別方式 | なし | Gaussian Splatting（gsplat・nerfstudioなど）、そこからメッシュを作る2DGS・PGSR | 見た目は強い。研究コードには非商用ライセンスのものが多い |
| 学習ベースの位置推定 | なし | MASt3R-SfM、VGGTなど | 模様の少ない屋内に強いとされる。ライセンスは個別に確認する |

RealityScan（旧RealityCapture）は、一定の売上以下なら無料で使えますがOSSではありません。Windows・NVIDIA GPUが必要です。商用品質の基準として比べられます。条件は変わることがあるので、使う前に公式で確認してください。

### 評価の軸

同じ素材で次の点をそろえて比べます。

1. 位置推定の正しさ：経路の飛び、1つの復元にまとまるか
2. 形の完成度：白い壁や床の穴、浮いた破片の量
3. テクスチャの質：にじみ、撮影者の写り込み
4. 処理時間とディスク・メモリの使用量
5. VRChatでの使いやすさ：作り直しの下敷きとして足りるか

### 撮影で効くこと

ソフトを替えるより、素材の質のほうが結果への影響が大きい可能性があります。

- 撮影者が写らない持ち方にする（頭上に高く掲げる、タイマーで物陰に隠れる）
- ゆっくり歩き、明るさを確保する
- 途中でカットしない。撮り直すときは、カットのない区間ごとに別の動画にする
- 可能なら、動画ではなく360度写真を数十cmおきに撮る

### 次に試すこと

1. 300万面＋床の処理で、陥没と粗さがどこまで減るかを見る
2. 白い壁の穴：`--free-space-support` と `--close-holes 300`（既定にした）の効果を見る。点群に壁の点がない場合は、点群統合や深度推定の条件を見直す
3. 高密度化をOpenMVS DensifyPointCloudに替えて、06〜07を比べる
4. 撮影方法を変えた素材で、同じ設定のまま比べる

## GPUの使い方

| 工程 | この構成での処理 |
|---|---|
| 動画デコード | 対応する形式はNVDEC（最初に指定したGPU）。失敗したら理由を表示してCPUで再試行 |
| 特徴点抽出・画像照合 | COLMAP CUDA、選択した全GPU |
| カメラ位置の推定（BA・全体位置） | cuDSS対応のCUDA版Ceres、最初に指定したGPU。問題の大きさによってはCeresがCPUを選ぶ |
| 深度推定 | COLMAP CUDA、選択した全GPU |
| 360度の投影変換・JPEG保存 | FFmpegのCPU処理 |
| 点群統合 | COLMAPのCPU処理 |
| メッシュ化・床の処理・テクスチャ | OpenMVS／CGAL・PythonのCPU処理 |

Ceresは、cuDSS（GPUの疎行列ソルバー）を含む未リリースの開発版を、コミットを固定してビルドしています。
OpenMVSはCUDAなしでビルドしています。今使っているReconstructMesh・TextureMeshは、CUDAを有効にしてもGPU化されません。

`run.sh` は、NVDECに必要なvideoドライバーライブラリをコンテナへ渡す設定を含みます。

## 開発

| ファイル | 内容 |
|---|---|
| mp4_to_model.py | パイプライン本体（コンテナ内で実行） |
| run.sh | Dockerで実行するためのラッパー |
| Dockerfile | FFmpeg・COLMAP・Ceres・OpenMVSのビルド |
| openmvs-opencv46.patch | OpenCV 4.6でOpenMVSをビルドするためのパッチ（JPEG XL書き出しだけを止める） |
| diagnose_frames.py、export_trajectory.py | 結果の確認用（ホストで実行） |
| test_pipeline.py | 模擬テスト |
| CHANGELOG-ja.md | 変更履歴と、各変更の原因 |

テストは外部コマンドを呼ばずに、工程の順序、再開、GPUの割り当て、床の処理などを確認します。

~~~bash
python3 -m unittest -v test_pipeline.py
~~~

Dockerfile・.dockerignore・openmvs-opencv46.patch・mp4_to_model.pyは、まとめて更新してください。
